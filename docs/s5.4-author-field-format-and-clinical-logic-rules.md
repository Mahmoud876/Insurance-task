# S5.4 — Author field format and clinical logic rules

This document captures the Phase 2 format and Phase 3 clinical validation rules for claim-author data and treatment logic. It follows the design doc requirement for 16 rule entries: 6 format rules in Phase 2 and 10 clinical rules in Phase 3. Each entry includes a fixture, a remediation hint, a path pointer to the relevant validator or normalization module, and a cited reference.

## Scope and placement

Relevant implementation surfaces in the current codebase:

- `app/domain/normalization/date.py` — date normalization and validation primitives
- `app/domain/normalization/money.py` — field/value normalization and error emission
- `app/domain/normalization/surface.py` — tooth-surface normalization and clinical token handling
- `app/domain/normalization/findings.py` — `Phase1Finding` and result contract used for validation findings
- `app/tests/domain/normalization/` — representative unit-test fixtures for normalization behavior

The rule catalog below should be implemented as Phase 2 and Phase 3 validators using the same `NormalizationResult` / `Phase1Finding` or equivalent reporting contract used by the current domain-normalization layer.

## Phase 2 — Author field format rules (6)

### F-02-01 — Author value must be non-empty after trim
- Description: Reject blank or whitespace-only author strings before clinical validation.
- Fixture:
  - Valid: `"Dr. Nguyen"`
  - Invalid: `"   "`, `""`, `null`
- Fix hint: Trim whitespace, return a validation finding with code `EMPTY_AUTHOR_INPUT` before downstream processing.
- Path pointer: `app/domain/normalization/findings.py`, `app/domain/normalization/date.py` style pattern for empty-input guards
- Reference: Design Doc S5.4, Phase 2, Rule 1; ADA claim-form author entry conventions

### F-02-02 — Collapse internal whitespace and normalize Unicode
- Description: Convert tabs/newlines/multiple spaces into a single space and normalize Unicode to a stable NFC form.
- Fixture:
  - Input: `"  Dr.\tNguyen   "`
  - Normalized: `"Dr. Nguyen"`
- Fix hint: Use `str.strip()`, then regex `\s+` collapse, followed by `unicodedata.normalize("NFC", value)`.
- Path pointer: `app/domain/normalization/date.py` normalization patterns for defensive string coercion
- Reference: Design Doc S5.4, Phase 2, Rule 2; Unicode normalization guidance (NFC) and claim-form data hygiene

### F-02-03 — Disallow control characters and invalid separators
- Description: Reject ASCII control characters and disallowed separators such as `\r`, `\n`, or repeated punctuation tokens in the author field.
- Fixture:
  - Valid: `"J. Doe"`
  - Invalid: `"J\nDoe"`, `"J\x00Doe"`, `"Dr.--Nguyen"`
- Fix hint: Strip control chars before validation; fail with `INVALID_AUTHOR_CHARACTERS` if a disallowed symbol remains.
- Path pointer: `app/domain/normalization/surface.py` token sanitization pattern for invalid-character rejection
- Reference: Design Doc S5.4, Phase 2, Rule 3; claim author form data validation best practices

### F-02-04 — Enforce author length bounds
- Description: Keep author records within the maximum supported author length to avoid truncation or malformed indexing.
- Fixture:
  - Valid: `"Dr. A. Patel"`
  - Invalid: `"A" * 256`
- Fix hint: Fail with `AUTHOR_LENGTH_EXCEEDED` when length is outside configured range (for example 2-120 characters).
- Path pointer: `app/domain/normalization/findings.py` result object contract for field-level findings
- Reference: Design Doc S5.4, Phase 2, Rule 4; claim record storage limits and UI input constraints

### F-02-05 — Require a valid name token structure
- Description: Author strings must contain at least one alphabetic token and valid separators such as comma, dot, hyphen, or space.
- Fixture:
  - Valid: `"Doe, Jane"`, `"Jane A. Doe"`, `"Dr. Jane Doe"`
  - Invalid: `"12345"`, `"---"`, `"@example"`
- Fix hint: Validate against an allowlist of name characters and confirm at least one alpha sequence is present.
- Path pointer: `app/domain/normalization/surface.py` token validation pattern (`VALID_SURFACE_CODES` + invalid token discovery)
- Reference: Design Doc S5.4, Phase 2, Rule 5; common name formatting standards for provider and author fields

### F-02-06 — Normalize and preserve a canonical author string
- Description: Output a single canonical representation before persistence or comparison, even when the author was entered in a variant format.
- Fixture:
  - Input: `" dr. jane doe "`, `"JANE DOE"`, `"Doe, Jane"`
  - Canonical output: `"Doe, Jane"` or `"Jane Doe"` per project policy; the key is consistency
- Fix hint: Apply canonical formatting only after validation; do not mutate hidden data in-place. Keep one canonical form for comparisons.
- Path pointer: `app/domain/normalization/money.py` canonical numeric normalization pattern; `app/domain/normalization/findings.py` result reporting
- Reference: Design Doc S5.4, Phase 2, Rule 6; canonical author naming convention for claim indexing and deduplication

## Phase 3 — Clinical logic rules (10)

### C-03-01 — Procedure code must be present and recognized
- Description: Every clinical line requires an explicit procedure code; unknown code values must trigger a clinical finding.
- Fixture:
  - Valid: `"D0120"`
  - Invalid: `""`, `"UNKNOWN"`
- Fix hint: Validate code against the procedure reference list before calculating readiness or totals.
- Path pointer: `app/domain/normalization/surface.py` invalid token detection and code acceptance pattern
- Reference: Design Doc S5.4, Phase 3, Rule 1; CDT code set and validation requirements

### C-03-02 — Claim date range must be logically ordered
- Description: The `service_date_from` value must be less than or equal to `service_date_to`.
- Fixture:
  - Valid: `from=2026-01-05`, `to=2026-01-15`
  - Invalid: `from=2026-01-15`, `to=2026-01-05`
- Fix hint: Normalize both dates using the `normalize_date` helper and compare them with a strict ordering check.
- Path pointer: `app/domain/normalization/date.py`
- Reference: Design Doc S5.4, Phase 3, Rule 2; claim-date integrity standard

### C-03-03 — Tooth numbers must be valid and within the dental chart range
- Description: Allow only valid tooth identifiers in the allowed chart range and reject impossible values.
- Fixture:
  - Valid: `"18"`, `"A"`, `"30"`
  - Invalid: `"0"`, `"99"`, `"Z"`
- Fix hint: Normalize tooth values early and fail with `INVALID_TOOTH_NUMBER` when outside the supported range.
- Path pointer: `app/domain/normalization/date.py` and `surface.py` as examples for defensive normalization and error codes
- Reference: Design Doc S5.4, Phase 3, Rule 3; ADA tooth numbering conventions

### C-03-04 — Surface tokens must be clinically valid for the selected tooth
- Description: Surface codes such as `M`, `O`, `D`, `B`, `F`, `L`, `P`, `I` must be valid and consistent with the selected tooth and procedure.
- Fixture:
  - Valid: `"MOD"`, `"B"`
  - Invalid: `"X"`, `"MODXYZ"`
- Fix hint: Use `normalize_surface` and reject any token set that includes unsupported characters or empty values.
- Path pointer: `app/domain/normalization/surface.py`
- Reference: Design Doc S5.4, Phase 3, Rule 4; surface coding standards in dental claim adjudication

### C-03-05 — Charge amounts must be numeric, non-negative, and finite
- Description: Line charge values must parse into a finite positive amount before inclusion in totals.
- Fixture:
  - Valid: `"125.00"`, `125`, `125.0`
  - Invalid: `"-1"`, `"NaN"`, `"abc"`, `null`
- Fix hint: Reuse `normalize_money` and reject non-finite or negative values before creating the claim total.
- Path pointer: `app/domain/normalization/money.py`
- Reference: Design Doc S5.4, Phase 3, Rule 5; billing integrity and claim-total validation

### C-03-06 — Total claim amount must equal the sum of line charges within tolerance
- Description: The header claim total must reconcile with the line items after normalization and rounding.
- Fixture:
  - Valid: lines `100.00 + 75.00`, total `175.00`
  - Invalid: lines total `175.00`, header total `170.00`
- Fix hint: Recompute totals from normalized line values and compare with a tolerance of 0.01 or the project-defined rounding rule.
- Path pointer: `app/domain/normalization/money.py` and `app/domain/normalization/findings.py` for result encoding
- Reference: Design Doc S5.4, Phase 3, Rule 6; claim reconciliation requirement

### C-03-07 — Missing author or clinician identifier must block clinical processing
- Description: A claim cannot be clinically accepted if the author or clinician identity is absent or malformed.
- Fixture:
  - Valid: `"Dr. Nguyen"`
  - Invalid: `""`, `"   "`, `"123"`
- Fix hint: Run the Phase 2 author-format validator before any Phase 3 eligibility or processing logic.
- Path pointer: `app/domain/normalization/findings.py` and the Phase 2 author validator path to be added alongside the present normalizers
- Reference: Design Doc S5.4, Phase 3, Rule 7; provenance and accountability requirement

### C-03-08 — Duplicate line entries with the same procedure/tooth/surface must be flagged
- Description: Repeated line items covering identical clinical targets are likely data-entry duplicates and should be reported.
- Fixture:
  - Valid: one line `D2740 / tooth 18 / MOD`
  - Invalid: two lines with same procedure, same tooth, same surface
- Fix hint: Group by `(procedure_code, tooth_number, surface)` and fail with `DUPLICATE_CLINICAL_LINE` when a duplicate appears.
- Path pointer: `app/domain/normalization/surface.py` grouping pattern and `findings.py` result contract
- Reference: Design Doc S5.4, Phase 3, Rule 8; claim integrity and duplicate prevention rules

### C-03-09 — Service date and procedure type must be clinically plausible together
- Description: A procedure may be invalid if the service date is outside the expected clinical timeframe or inconsistent with the patient history.
- Fixture:
  - Valid: routine exam with service date in range
  - Invalid: endodontic procedure with impossible date or future date beyond policy window
- Fix hint: Use the service date normalize helper, then compare to procedure-specific policy windows or business constraints.
- Path pointer: `app/domain/normalization/date.py` and the claim service validation path
- Reference: Design Doc S5.4, Phase 3, Rule 9; clinical plausibility checks and adjudication policies

### C-03-10 — Claim must carry a valid readiness outcome after all Phase 2 and Phase 3 checks
- Description: The final claim readiness state is a composite of format validation, clinical validation, and reconciliation checks.
- Fixture:
  - Valid: all 16 rules pass
  - Invalid: any one of the format or clinical rules fails
- Fix hint: Aggregate all findings into a single readiness summary and surface the highest-severity issue first.
- Path pointer: `app/domain/normalization/findings.py` and the claim scrubbing service flow
- Reference: Design Doc S5.4, Phase 3, Rule 10; final claim-readiness score and summary requirements

## Recommended implementation pattern

Follow the existing normalization contract used by the current codebase:

```python
result = normalize_date(raw_value, field_name="service_date")
if not result.is_valid:
    findings.append(result.finding)
```

Use the same approach for author-format and clinical validation:

- Normalize raw values into canonical forms
- Return `NormalizationResult(value=..., finding=None)` on success
- Return `NormalizationResult(value=None, finding=PhaseXFinding(...))` on failure
- Aggregate the findings list at the claim-scrub layer
